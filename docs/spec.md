# わちゃメーター 仕様

最終更新: 2026-11-11。ユーザーから確認できた構想と未決事項を記録する。調査上の提案は [初期調査](research/feasibility.md) に分ける。接続方式・採点式は未採用。

## 1. これは何か

集まったメンバーがどれくらい「わちゃわちゃ」しているかを測るアプリ。
Zoom などのオンライン会議ツールに1参加者として参加して様子を観測し、会議終了時に「わちゃわちゃ」の度合いをスコアとして参加者に知らせる、という体験を目指す。

最初に実現方法を調査し、その結果から試作・開発を進める。Web アプリ、デスクトップアプリなどの実装形態はまだ決まっていない。

## 2. 中身

現時点で確認できた利用の流れ:

1. オンライン会議にわちゃメーターが参加する。
2. 集まっているメンバーの「わちゃわちゃ」を観測する。
3. 会議終了時にスコアを参加者に知らせる。

他の人が主催する会議への参加が必要。主催者とユーザーが同じ Zoom 契約に属するかは不明なので、別アカウント主催の会議も対象にして成立条件を検討する。

会議には「わちゃメーター」が1参加者として入る。録音ファイルの解析だけに置き換えず、まずボットの入室と音声取得を優先して検証する。

招待方法、観測データ、スコアの範囲・計算式、結果の通知先・通知手段は未決。会議全体に対するスコアを構想の出発点とし、個人別の採点は依頼されていない。

## 3. 決まりごと

- 仕様の言語は日本語。
- 費用条件: 無料でできる構成を基本とする。ただし、Zoom の有料アカウントで実現できる構成は候補に含めてよい（ユーザー確認済み）。Zoom の契約費とアプリの追加費用を分ける。有料ボット API・有料 AI API・有料サーバーは前提にしない。期限付き無料体験だけで継続利用できるとは扱わない。
- 最初の試作は今使っている Mac で動かす（ユーザー承認済み）。接続試作は開発時と実行時の両方で、既存の OrbStack / Docker 上の ARM64 Linux を使う。完成版の Docker 利用・配布形態・最終方式は未決。
- 接続試作の技術判断: SDK 呼び出しは Docker 上の C++、設定・JWT・結果判定・プロセス管理は TypeScript に分ける（[ADR 0001](decisions/0001-zoom-sdk試作はDocker上のC++とTypeScriptに分ける.md)）。SDK は 7.2.1.5860 の arm64、JWT の有効期間は 3600 秒とする（[ADR 0002](decisions/0002-zoom-sdkは7.2.1.5860のarm64を使う.md)）。この採用は、ボット用途・外部会議参加の条件が解消したことを意味しない。
- OAuth の認可・トークン取得は Mac の Node.js で動かし、SDK と OAuth の設定は部品ごとの `.local/*.env` に分ける（[ADR 0003](decisions/0003-zoomアカウント連携はmacのnodeで動かし設定は部品ごとに分ける.md)）。Mac 側のトークンを Docker の SDK へ渡す設計は後続で行う。
- 「わちゃわちゃ」の定義はユーザーとの議論で決める。音量・発言量・楽しさを同一視した採点式を推測で実装しない。
- 会議への参加方法は各サービスの公式仕様に基づいて検討する。
- 実会議の音声・映像・文字起こし・参加者情報・参加 URL・認証情報を公開リポジトリに保存しない。
- 観測の告知・許可、外部サービスへの音声送信、保存期間は実会議検証前に決める。

## 4. 区切り

### 区切り1: Zoom に別参加者として入り、音声を取得する試作

2026-11-07 にユーザーが範囲を承認した。

- 対象: Zoom。他の人が主催する会議を対象とする。同じ契約内か不明のため、外部アカウント主催の場合も成立条件に含める。
- 同席条件: 最初のお試しではユーザー自身も通常の Zoom クライアントで同席する（2026-11-09 確認済み）。本人とは別に「わちゃメーター」が参加する。本人不在での参加は今回の試作範囲に含めない。
- 実行環境: 今使っている Mac。
- 費用: 無料で開始。Zoom の有料会議プランが必要と分かった場合は、理由を提示して相談する。追加課金 API・Developer Pack を前提にしない。
- 達成の確認: 主催者の参加者一覧に本人とは別の「わちゃメーター」が表示され、主催者の許可後に音声データを取得できる。その後退出できる。
- 待機室で待つだけ、入室だけ、手元の録音ファイルを解析するだけでは、この区切りを達成したと扱わない。
- 現状: Issue #1 は完了し、[PR #2](https://github.com/dyamada-jaki/wacha-meter/pull/2) を main（`0dd6388`）へ取り込み済み。SDK **7.2.1.5860（Linux-all バンドル内の arm64）** で、初期化・本物の認証情報による認証成功・後始末を確認した（2026-11-08 16:02:50 JST、`b015f2b`、許可を受けたワーカーによる実行）。Issue #4 の OAuth 連携コマンドも PR #5（main `0bec6f1`）で取り込み済み。2026-11-11 に本人から OAuth トークン取得成功・終了コード0の報告を受けた（Issue #7）。会議には参加していない。区切り1は未達で、用途・外部会議のテスト条件、入室・音声取得・退出の確認が残る。証拠は [Issue #1 レポート](issue-reports/issue-1.md)。

作業の順序は SDK 入手とビルド → 初期化・認証 → 外部会議用のテスト条件を満たす → 入室 → 許可を受けて音声取得 → 退出。個別問い合わせは準備作業の開始条件にしない。

### 次の準備: Zoom アカウント連携（Issue #4）

本人同席で進める試作の前段として、既存 General App の開発用設定を使い、Mac 上で本人が OAuth を許可してトークン取得成功を確かめる。今回の設定案内に対するユーザーの実施報告を受け、PO が以下を Issue #4 の範囲とする。外部会議への参加方式の採用・用途承認とは分ける。

- 設定済み（ユーザー報告）: Public Client OAuth は ON。Redirect URL for OAuth と OAuth Allow List は `http://127.0.0.1/callback`。スコープは `user:read:token`。実際の認可は2026-11-11に成功（本人報告、詳細は下記）。
- コマンドからブラウザの Zoom 認可画面へ進み、本人の許可後に成功・失敗を確認できる。公開サーバー・有料トンネルは前提にしない。
- Public Client ID を使った PKCE（S256）と `state` 検証を行う。SDK の Client ID / Secret と区別し、既存の SDK 認証設定を壊さない。Public Client ID のローカル設定手順は [試作の README](../prototypes/zoom/README.md) に用意済み。
- 一時 HTTP サーバーは Mac の loopback（`127.0.0.1`）のみで待ち受ける。認可拒否、不正な応答、時間切れ、中断を成功と扱わず、完了・失敗・中断で待受を閉じる。期限・中断時の表示などの具体値は計画で示す。
- 認可コード・トークン・秘密の値を画面・ログ・Git に出さない。取得したトークンはプロセス内のメモリで扱い、終了時に破棄する。この段階では永続保存・自動更新を導入しない。
- 本人によるログイン・許可と、エージェントによる自動検証を分けて記録する。実認可未確認を Issue 完了と扱わない。人間の操作を PR 作成条件にはしない。
- 今回は会議への接続、OBF 取得・入室、音声取得、採点、結果画面、外部配布、Zoom への申請送信を行わない。既存の SDK 初期化・認証機能を維持する。

#### 2026-11-10 の取り込みと持ち越し

人間が「テストするのが今は難しそうなので、いったん #5 をマージして閉じようと思います」と判断し、PR #5 を main `0bec6f1` に取り込み、Issue #4 をクローズした。169件の自動テストと CI は成功したが、**本人のログイン・許可・実トークン取得（受け入れ条件1）は未確認**。上記の完了条件に対して、未確認を明示して閉じた個別の判断であり、実認可の合格・区切り1の達成・POの受け入れとは扱わない。

残作業は [Issue #7](https://github.com/dyamada-jaki/wacha-meter/issues/7) に引き継ぐ。本人がテストできる状況になったときに、対象 SHA・結果・終了コード・待受の後始末を記録する。以前の worktree にあった OAuth の設定ファイルは削除済みなので、再開時は main の設定の有無を確認する。詳細の正本は [Issue #4 レポート](issue-reports/issue-4.md)。

#### 2026-11-11 の実認可確認（Issue #7）

本人から、認可の応答後に OAuth トークンを取得でき、終了コードが `0` だったとの報告を受けた。表示は種類 `bearer`、有効期間3599秒、スコープ `user:read:token`。実行案内時と結果受領時の main は `861f8d8e528bb66ae97fa9928067ff43543292bd`、Mac / Node.js 24.14.0。正確な実行時刻は未採取。対象の OAuth コード・テスト・package 設定に PR #5 取り込み後の差分はない。PO による再認可は行っていない。

一時待受はトークン要求前に閉じる実装と、シェルへ戻って終了コード0を確認できた本人報告を根拠に、終了を確認した。対象ポートへの接続確認は別途行っていない。今回の試作はトークンを保存しないため、今後トークンが必要な検証では再認可する。実認可の持ち越しは解消し、同日のユーザーの「#7の仕様を採用します」により下記の仕様も確定した。Issue #7 の残件は解消。

以下は2026-11-11に人間が採用した OAuth 確認コマンドの仕様。トークン取得の成功と、その後の API が必要とする権限の充足は区別する。

- 成功条件: HTTP 200・空でない `access_token`・bearer の `token_type`・正の `expires_in`。`scope` はなくても成功。
- エラーコードの表示範囲: `[A-Za-z0-9_]{1,64}`。
- トークン要求のリダイレクトは失敗にする。
- GET 以外・対象外パス・2回目以降の callback は404。URL解析不能な要求は400を返して期限内で待ち続ける。

### 次の準備: OBF トークンの取得確認

OAuth の実認可成功とユーザーの進行指示を受け、PO が次の実装を、本人に紐づく参加用トークン（OBF）の取得確認に切り出す。会議参加方式の採用・用途承認とは分ける。

- Mac 上で本人が OAuth を許可し、同一プロセス内で得たアクセストークンから OBF を要求する。追加課金サービスは前提にしない。
- 要求先は `GET https://api.zoom.us/v2/users/me/token?type=onbehalf`。今回は会議番号を指定せず、取得のみを確認する。会議番号が必要との応答があれば失敗を記録し、PO に戻して範囲を見直す。
- HTTP 200 と空でない文字列の OBF トークンを確認した場合だけ取得成功と表示する。OAuth だけの成功、権限不足、期限切れ、不正な応答、通信失敗、時間切れ、中断を OBF 成功と扱わない。
- OAuth・OBF の値をメモリだけで扱い、画面・ログ・引数・環境変数・ファイルに出さず、終了時に破棄する。保存・自動更新を導入しない。
- 正常・失敗・中断時に一時待受を閉じる。既存の OAuth・SDK 認証コマンドの振る舞いを維持する。コマンド名、期限、終了コード、安全なエラー表示は開発チームの計画で示す。
- 自動テストと本人による実 API 確認を分けて記録する。実確認は PR 作成条件にしないが、未実施を取得成功や Issue 完了とは扱わない。
- スコープ外: SDK への受け渡し、会議入室・退出、音声取得、採点、外部配布・申請送信・課金。

テスト会議については、ユーザーがいつでも使える会議室を持ち、本人の入室はいつでも可能と報告した。2026-11-11に、主催は他の人のアカウントと確認できた。同じ Zoom 契約内かは不明。ボットの入室許可・音声観測の許可や、別契約の会議への参加成功は未確認。

### 以降の区切り（案・未採用）

音声取得の見通しが立った後に、わちゃわちゃの指標・採点方法と画面デザインを決める。その後、短い会議での指標を参加者の実感と照らし、会議終了後の結果提供までつなぐ。

### 今はやらないこと

調査段階では、本番会議への接続、採点式の確定、課金サービスへの契約・課金実行を行わない。
