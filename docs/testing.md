# テストとレビューの方針

振る舞いの正本は [spec.md](spec.md)、今回の範囲は GitHub Issue に置く。この文書は、仕様をどう確かめ、変更をどうレビューするかを決める。Codex と Claude Code は同じ方針を使う。

現在はオンライン会議の観測アプリの調査・準備段階。TypeScript の共通基盤だけがある。接続方式・採点ルールが確定した機能からテスト先行で実装する。

`npm run test:setup` は準備段階だけテスト0件を許可する。最初の機能 Issue で CI・開発設定を `npm run test` に切り替える。0件の成功をアプリの検証済みと扱わない。

## 1. 実装前に決めること

- 受け入れ条件ごとに、入力・操作・期待結果と、確かめる層を計画に書く。期待結果は仕様から決め、実装の出力をそのまま正解にしない。
- 正常な例だけでなく、境界、選択の切り替え、操作しても変わらない場合など、その変更で間違えやすい点を選ぶ。仕様にない入力制約やルールはテストにも追加しない。
- 特に間違えやすい点は、少数の「壊れ方の具体例 → 仕様上の期待 → 検出するテスト／確認方法」として計画に書く。たとえば「別の項目を押すと選択ではなく移動してしまう」「解除後に再選択できない」「ラベルだけ画面外へはみ出す」など。基盤変更では起動途中の中断や既存資源への影響も、対象の保証に応じて選ぶ。既存の受け入れ条件との対応を示し、すべての仮想的な故障を網羅するために範囲を広げない。
- **機能追加・振る舞いの変更では、テストを先に書いてから実装する（テストファースト）。** 計画で決めたテストを実装より先に書いて実行し、**対象の振る舞いが未実装、または誤っているために失敗する**ことを確かめる。期待値と結果の不一致だけでなく、未実装の画面要素が見つからないことも含む。環境設定の不備や無関係な import・型エラーは、対象の振る舞いを検証できた証拠にしない（関数や部品の空の枠だけ先に作ってよい）。そのテストを実装より前のコミットにし、そのあと実装して通す。PR のコミット履歴と本文で、この順番が分かるようにする。
  - 単位は受け入れ条件（振る舞い）ごとでよい。関数ごとの細かな Red → Green → Refactor の繰り返しまでは求めない。計算や状態遷移で役立つなら使う。
  - 実装中に必要と分かったテストは追加してよい。ただし、先に書いたテストを実装に合わせて弱めない。
  - 振る舞いを変えないリファクタリングでは、既存テストが変更前後で通ることを確かめる。既存テストが不足していれば、変更前に現在の振る舞いを確認するテストを追加して通す。新しく失敗するテストを作る必要はない。
  - 対象外：テストで確かめる振る舞いのない変更（文書・設定・依存の更新など）。E2E は先に書けるなら先に書き、環境の都合で書けない場合は実装と同時でよい。
  - 先に書けなかったテストがあれば、理由を PR に書く。
- アプリの不具合修正では、原則として修正前に失敗する再現テストを作り、修正後に通ることを確かめる。実機だけで起きるなど自動化できない場合は、再現手順・修正前後の結果・自動化できない理由を PR に残す。
- 期待値や検証条件を変えるときは、根拠となる仕様または元のテストの誤りを説明する。通すためだけに assertion を減らしたり、失敗するテストを無効化したりしない。

## 2. テストの層と分担

| 層 | 主に確かめること | 方法 |
|---|---|---|
| Vitest：観測データから結果まで | 決定した仕様の入力・期待結果、集計・採点の境界 | 公開された処理の入口を通し、手で計算した期待値と比較する。採点式の未決部分はテストにも推測で追加しない |
| Vitest：外部接続の結合（導入後） | 会議サービスから受け取るデータを集計へ渡す流れ | 外部サービスの境界だけを fake にする。SDK の接続自体は実会議検証と分ける |
| 実会議での検証（導入後） | 入室・観測権限・参加者別音声・退室・終了後の結果 | 許可されたテスト会議で確認する。ホスト終了とボット単独退出を区別できるか、欠測と無言を区別できるかも仕様化して確かめる |
| 人間による妥当性確認 | スコアが参加者の感じた「わちゃわちゃ」と合うか | 同じ短い会議に対する主観評価と照らす。音声取得成功をスコアの妥当性確認と混同しない |
| UI・E2E（画面導入後） | 設定から結果確認までの操作 | 採用する UI と表示幅を決めてから導入する |

現在の調査資料は、公式資料の参照先・確認日、事実と提案の区別、未確認条件をレビューする。動作未検証の SDK や API を動作確認済みと書かない。

テスト件数だけで品質を判断しない。文書や設定だけの変更に、実装をなぞるテストは増やさない。

## 3. モックは必要な境界だけに使う

**古典派を基本にし、実物を使った結果の検証を優先する。** 純粋関数、React の部品、アプリ内の状態管理を、それぞれモックに置き換えて結合を失わないようにする。

- 外部サービス、時刻、乱数など、遅い・不安定・副作用がある境界では、stub・fake・mock を使ってよい。使う理由と、実物との接続をどこで確かめるかを計画と PR に書く。
- 呼び出し回数や内部の手順より、戻り値・表示・保存された状態などの結果を検証する。外部送信の重複防止など、呼び出し自体が契約になる場合は、その理由を明示して検証する。
- テストごとに状態を独立させる。実物を使う場合も、本番データや実際の外部送信先を使わない。将来サーバーや DB を導入したときは、可能な範囲で隔離した実物のテスト環境を使う。
- スナップショットだけで操作や計算の正しさを判断しない。利用者が観察できる結果を明示して確かめる。

## 4. E2E とミューテーションテスト（導入したら）

どちらも、導入するときは専用の Issue で行い、ここに対象・実行方法・結果の読み方を書く。未導入なのに確認済みと書かない。

- **E2E**：重要な流れを少数に絞り、実際のアプリを実ブラウザで開いて確かめる。要素は role や表示名を優先して特定し、固定時間ではなく期待する状態を待つ。再試行で通っただけの不安定なテストを正常と扱わない。ブラウザでの確認で、人間の実機確認を済ませたことにはしない。
- **ミューテーションテスト**：実装の条件式などを一時的に変え、テストがその誤りを見つけるかを確かめる。通常テストが成功してから実行し、生き残った変異は「テスト不足／等価な変異／対象外／判断待ち」に分けて根拠を残す。一律のスコア閾値は導入時に決めない。
- CI が重くなったら、省略やキャッシュを入れる前に「実際に検証した内容との差分で決める」ことを確かめる（PR の head などを比較元にすると、検証していない内容を省略しうる）。

## 5. PR レビューの分担

レビュー対象は PR の説明や差分だけではない。Issue・仕様を起点に、**変更された実コードとテスト、その呼び出し元・依存先・関連する既存テスト**まで、影響を判断できる範囲で読む。無関係な箇所まで全リポジトリを精査することは求めない。

| 担当 | 主な責任 |
|---|---|
| 相互レビュー担当 | 受け入れ条件を1つずつ判定し、仕様との一致、バグ・回帰、スコープ、検証の証拠を確認する。対象コミットで必須チェックを再実行する。UI では変更に関係する主要操作もブラウザで確かめる |
| 独立した品質レビュー担当 | 新しいセッションで、責務の分け方、状態の重複・同期、依存の向き、型や境界の扱い、過剰な抽象化、変更のしやすさ、テストが誤りを捕まえるかを確認する |
| コーディネーター | 指摘を実コードと仕様で裏付け、重複・誤検出を整理する。今回直すものと別 Issue の候補を分け、採用判断を人間に示す |
| 人間 | 実機の使いやすさと仕様上の判断を確認し、採用する PR を決める |

品質レビューは、人間が明示的に指定した場合に追加する。PR ごとに実装・相互レビューとは別のセッションを使い、他者のレビュー結論を読む前に自分の確認結果をまとめる。相互レビューとの同時実行は可能だが、別の worktree を使い、同じファイルやコンテナを操作しない。役割名だけで品質が上がったとは判断しない。

### 二重実装と品質レビューの評価

続けるかを判断するときは、二重実装の比較で得た価値と、独立した品質レビューの追加価値を分けて評価する。

- **得られた改善**：具体的に確認できた不具合・回帰・検証不足、採用した設計やテストの観点と、その後の修正・再確認。提案の採用と実装完了を区別し、後続へ引き継いだものも結果を追う。
- **独自性**：どの担当・比較で初めて確認できたか、相互レビューと重複したか。指摘件数をそのまま成果として数えない。
- **手戻りと負担**：誤検出・判断できなかった指摘と、その調査や修正に要した手戻り。担当別の時間と追加待ち時間は6章の方法で記録し、費用・トークン量など未計測の値を推定で補わない。
- **判断**：品質への具体的な寄与を優先し、継続／対象を絞る／終了／材料不足で継続観測の案と根拠を示す。比較するIssueの規模・性質・対象SHAの違いを考慮し、モデル全般の優劣や「担当がいなければ必ず見逃した」といった反実仮想は断定しない。材料不足なら追加で確かめる対象と判断時点を示す。

### 対象コミットと確認結果

- レビュー開始前に PR の `headRefOid` を記録し、作業場所の `HEAD` と一致することを確かめる。相互レビューと品質レビューは同じコミットを対象にする。未コミットの変更があれば、そのままレビューしない。
- 相互レビュー担当は「開発設定」の確認コマンドと、導入済みで対象となる E2E を実行する。品質担当は重複実行を必須にせず、構造とテスト内容を重点的に読む。実行が必要なら自身の隔離された作業場所で行う。
- 実行できないチェックは、理由と未確認の範囲を記す。CI・実装者の報告・自分で再確認した結果を区別し、未確認を「合格」にしない。
- 修正で head が変わったら、古いレビューはそのまま採用判断に使わない。更新差分と影響範囲を再確認し、新しい SHA と確認結果を残す。修正が不要だった場合も、報告時とマージ前に head が同じか確かめる。

### 指摘の書き方と扱い

1件ごとに、対象 SHA、ファイルと行、発生条件または具体的な影響、根拠（仕様・コード・再現結果）、修正案を付ける。確認できない懸念は、事実と分けて「未確認」と書く。

- **必須**：受け入れ条件を満たさない、仕様に反する、再現できるバグ・回帰など、今回の完了を妨げるもの。採用前に解消し、再確認する。
- **推奨**：具体的な保守・変更上の負担やテストの弱点があり、改善する価値があるもの。今回のスコープに必要なら修正し、独立した改善なら後続 Issue の候補にする。
- **好み**：振る舞いや具体的な保守上の影響がない表現上の違い。原則として採用を止める理由にしない。

推測上の将来要件に備えるだけの抽象化や、好みだけの全面改修を求めない。コーディネーターは各指摘を「確認できた／誤り／判断できない」に分け、確認できたものの対応先と、除外した理由を残す。

## 6. 証拠を残す

- **計画**：受け入れ条件と検証方法、仕様から決めた代表例・期待結果、モックを使う場合の理由、E2E の対象または対象外の理由。
- **PR**：対象コミット、実行コマンド・環境・結果、画面の幅・操作・結果、未確認の条件。期待値を変更した場合は根拠も残す。
- **ミューテーションテスト**：導入済みで対象となる場合は、実行範囲・結果・生き残った変異の判断と対応先をPRに残し、レビューとIssueレポートへ引き継ぐ。
- **レビュー**：担当と役割、対象 SHA、読んだ周辺コードの範囲、自分で実行した確認と他者の証拠、指摘と残る不確実性。
- **[Issue レポート](issue-reports/README.md)**：両レビューの結果とリンク、コーディネーターの確認、修正後の再確認、採用理由。品質レビューを加えたときは、相互レビューと重複しなかった有効な指摘、誤検出と除外理由、追加の所要時間も残し、続けるかの判断材料にする。時間を測れなければ推定値で埋めず「記録なし」とする。

所要時間は担当ごとの開始・終了時刻で記録する（finish-issue が作業時間の表を作る）。「追加待ち時間」は相互レビューがそろってから品質レビューがそろうまでの時間とし、品質レビューが先に終わっていれば0とする。
