# 外部会議への接続検証案

確認日: 2026-11-09。PO による次の検討。実装・アプリ設定変更・申請・会議接続は未実施。本人の同席はユーザーが確認済み。それ以外の仕様案と Issue 分割は着手前の検討事項。現在の確定事項は [spec.md](../spec.md)、前段の完了記録は [Issue #1](../issue-reports/issue-1.md)。

## 今回分かったこと

| 条件 | 確認した内容 | この試作への影響 |
|---|---|---|
| SDK 認証と外部会議参加 | SDK の JWT に加え、アプリを OAuth で許可した参加者に紐付く OBF トークンを使う。本人の入室前は参加できず、本人が退出すると SDK セッションも終了する | #1 の認証成功だけでは外部会議には入れない。ご自身も同席する形で試す（ユーザー確認済み） |
| 外部会議のベータテスト | Request to Share の承認後、認可 URL を外部の主催者へ共有する手順がある。Technical Design とセキュリティ資料等の提出が必要 | 会議 URL と主催者の口頭許可だけでは準備完了にならない |
| ローカルの OAuth | Public Client OAuth / PKCE と loopback redirect により、Mac 上のブラウザからローカルの一時 HTTP サーバーへ認可応答を戻せる | 公開サーバー・有料トンネルを前提にせずアカウント連携を試せる。既存アプリでの設定可否は未確認 |
| OBF 取得 API | `GET /v2/users/me/token?type=onbehalf`。粒度の細かいユーザー用スコープは `user:read:token`。API は `meeting_id` パラメーターも持つ | SDK の Client Secret だけで代用しない。対象会議とアプリ設定に合わせて取得を検証する |

根拠: [OBF 認証](https://developers.zoom.us/docs/meeting-sdk/auth/obf/)、[認証変更 FAQ](https://godevelopers.zoom.us/docs/meeting-sdk/obf-faq/)、[外部ベータテスト](https://godevelopers.zoom.us/docs/distribute/sharing-private-and-beta-apps/)、[OAuth / PKCE / loopback](https://developers.zoom.us/docs/integrations/oauth/)、[Users API](https://developers.zoom.us/docs/api/users/)。

費用面では [Zoom の認証方式比較](https://developers.zoom.us/blog/app-attribution-path/) が OBF の SDK 利用を無料と説明している。これは会議プラン・用途承認・将来の配布費用まで無料と保証するものではない。今の Mac と既存 General App を使う候補とし、追加課金は前提にしない。

## 用途に関する未解決点

[Meeting SDK 概要](https://developers.zoom.us/docs/meeting-sdk/) と [Linux 概要](https://developers.zoom.us/docs/meeting-sdk/linux/) は、人間向けの用途でボットや AI 議事録アプリをサポートしないと記載している。一方、上記の OBF 専用文書はボットの参加を説明し、[Zoom の公式ブログ](https://developers.zoom.us/blog/app-attribution-path/) も、参加者として見えるアプリの経路に OBF を挙げている。新規の「わちゃメーター」が認められるかまでは確定できない。

[フォーラムの同じ疑問](https://devforum.zoom.us/t/question-on-linux-sdk-usage-policy/141545) には、本人が同席しないボットへの対策だという説明がある。ただし回答者は Independent MVP で、Zoom による個別用途の承認として扱わない。

PO の提案は、本人が同席する OBF 経路を検証候補に絞り、アカウント連携の準備を進めること。外部会議への実接続までには、用途とベータ共有の承認条件を確認する。通常の Zoom 有料プランへの変更だけで解決すると仮定しない。申請を準備する際は「参加者として入り、許可を受けて音声から会議全体の活発さを測る」という用途をそのまま示す。個別問い合わせは全準備の開始条件にしない。

## 最初に試す体験の案

1. ユーザーが Mac 上で連携コマンドを実行し、ブラウザの Zoom 画面でアプリを許可する。
2. 協力者が開く短いテスト会議に、ユーザー自身が通常の Zoom クライアントで参加する。
3. わちゃメーターを本人とは別の参加者として入れる。待機室では主催者が入室を許可する。
4. 最初の接続テストでは入室・退出を確認する。音声受信は次の段階に分ける。
5. 本人の退出時にも、わちゃメーターが退出して接続・コンテナが残らないことを確認する。

試験時間は5〜10分を候補とする。協力者の有無はユーザーへ確認中。本人が同席する条件はユーザー確認済みで、本人不在で参加する機能はこの案に含めない。同一契約内のテストを行った場合は、外部会議の検証とは分けて記録する。

音声受信の段階では、主催者・参加者への説明と許可の取り方を決める。初回は音声ファイルを保存せず、受信した量・時間だけで成立を確かめる案。保存方針と採点仕様は未決のまま。

## Issue #4: 自分の Zoom アカウントを手元の試作に連携する（着手条件確認待ち）

目的: 外部会議で必要になるユーザー認可を、入室処理から切り離して検証する。既存 General App の開発用設定を使い、無料で始められるローカルの OAuth 経路を用意する。

着手前に確認すること:

- 本人の同席は確認済み。Zoom の実際のログイン・アプリ許可は検証時に本人が行う。
- 既存 General App のユーザー認可方式、Public Client OAuth、`user:read:token`、loopback redirect の設定可否。既存の SDK 認証用 Client ID と、OAuth の Public Client ID を混同しない。
- 実認可時の操作分担・試行回数・期限を計画で決める。ログイン・許可操作は人間が行い、秘密の値をチャットへ貼らない。

受け入れ条件案:

- コマンドからブラウザの Zoom 認可画面へ進み、許可後にローカルの試作で OAuth トークン取得成功を確認できる。
- PKCE（S256）と `state` 検証を行う。認可拒否・不正な応答・時間切れ・中断を成功と扱わない。
- 待受は loopback のみ。完了・中断・失敗で一時サーバーを閉じる。秘密の値・認可コード・トークンを画面、ログ、Git に出さない。
- 最初の検証ではトークンをメモリで扱い、終了時に破棄する案とする。保存・自動更新はこの段階で導入しない。
- 外部 API 境界を使った自動テストと、人間が操作する本物の OAuth の確認を分けて記録する。実認可未確認を完了とは扱わない。
- Issue #1 の SDK 初期化・認証機能を維持し、既定のテスト・型チェック・Lint・ビルドを通す。

スコープ外: 会議参加、OBF を使った入室成功の判定、音声取得、採点、結果画面、外部配布、課金、ベータ共有申請の送信。

この案はアカウント連携の準備であり、ボット用途や外部会議参加の承認を代替しない。実装方法の詳細と期限の値は開発チームの計画で具体化する。[Issue #4](https://github.com/dyamada-jaki/wacha-meter/issues/4) として先行登録済み。受け入れ条件は案のままで、設定可否の確認と spec.md への反映後に着手を判断する。「開発可」は未付与、開発チーム未起動。

## その後の分割案

- 外部会議での入室・退出: 上の連携に OBF 取得と SDK 入室をつなぐ。用途・外部ベータの条件、主催者の協力がそろってから実接続する。待機室・入室成功・拒否を分け、本人の退出時も確認する。
- 許可を受けた音声受信: 音声取得の権限、許可前・拒否・取消時の扱い、受信の証拠、保存条件を決めてから実装する。入室成功だけで区切り1の達成としない。

[ADR 0001](../decisions/0001-zoom-sdk試作はDocker上のC++とTypeScriptに分ける.md)・[ADR 0002](../decisions/0002-zoom-sdkは7.2.1.5860のarm64を使う.md) を引き継ぐ。手元の 7.2.1.5860 のヘッダーに入室状態・待機室状態と OBF 関連の入力欄があることは確認したが、具体的な入力欄の選択と実 SDK での動作は実装計画・検証で確かめる。
