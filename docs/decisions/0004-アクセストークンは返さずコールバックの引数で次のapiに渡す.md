# 0004. OAuth のアクセストークンは戻り値で返さず、コールバックの引数として次の API に渡す

- 状態: 採用
- 日時: 2026-11-12 22:19 JST
- 関連: Issue #8 / 採用 PR #9 / [Issue レポート](../issue-reports/issue-8.md)

## 背景
Issue #8 で、本人の OAuth（`npm run zoom:oauth` の流れ）に続けて、同じプロセスの中で OBF トークンを取得するコマンド（`npm run zoom:obf`）を作った。OAuth で得たアクセストークンを Users API に渡す必要がある一方、Issue #8 では値を画面・ログ・引数・環境変数・ファイルに出さず、メモリだけで扱って終了時に捨てることが条件だった。既存の `exchangeCode` はトークンの値を返さない作り（Issue #4）なので、値の渡し方を決める必要があった。

## 決定
- アクセストークンは関数の戻り値・結果の型に入れない。トークンを使う後続処理を、OAuth の流れにコールバック（`UseAccessToken<U> = (accessToken, signal) => Promise<U>`）として渡し、トークン取得と検証の成功後に、その引数としてだけ渡す（`src/zoom-oauth/token.ts`）
- コールバックの結果は総称型 `U` で返す。例外は値を含みうるので、本文を持ち出さず「投げた」ことだけを返す（`UseResult<U>`）
- コールバックを渡さない呼び出し（`zoom:oauth`）の振る舞いは変えない。リフレッシュトークンは使わずに捨て、保存・自動更新はしない
- 次の Issue の計画で守ること: OAuth・OBF などのトークンを使う処理を増やすときも、値を戻り値・ログ・例外のメッセージに載せず、この接続点から引数で渡す。Docker の SDK へ渡すときは、[0003](0003-zoomアカウント連携はmacのnodeで動かし設定は部品ごとに分ける.md) のとおり渡し方を計画に書き、この原則（値を外に返さない）との関係を示す

## 理由
- 二重実装（PR #9 / PR #10）の両計画が、同じ「コールバックの引数で渡す」選び方をした
- 値を返さなければ、呼び出し元が誤って表示・保存する経路が型の上で生まれない。テストでは、偽の秘密値が出力に出ないことを確かめればよい
- PR #9 の形（結果を総称型で返し、例外を `threw` に畳む）は、既存の `zoom:oauth` の表示・終了コードを変えずに接続点を足せた（[比較](../issue-reports/issue-8.md#4-実装の比較)）

## 選ばなかった案
- アクセストークンを戻り値で返し、呼び出し側で次の API を呼ぶ: 値がモジュールの外へ出て、表示・保存の誤りを防ぐのが呼び出し側の注意だけになるため
- PR #10 の形（`onAccessToken(accessToken) => Promise<void>` で結果を外側の変数に入れ、例外は外へ伝える）: 結果の受け渡しが型で表れず、例外の本文が外に出うるため

## 影響
- 後続の API 呼び出しは、OAuth の流れの中（同じプロセス・同じ中断信号）で行う形になる。中断と上限時間は、後続処理の側でも受け取った `signal` と自分の上限で扱う必要がある（Issue #8 では、応答本文の受信後にも中断・上限を確かめる）
- トークンをプロセスの外（Docker の SDK など）へ渡す必要が出たときは、この決定だけでは足りない。渡し方を新しく決め、必要ならこの ADR を置き換える
- 見直すきっかけ: トークンの保存・自動更新が必要になったとき、または OAuth と後続処理を別プロセスに分ける必要が出たとき
