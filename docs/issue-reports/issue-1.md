### 計画の要点

- **Claude Code**: C++ の検証プログラム（`init` / `auth <秒>`、結果は JSON 1行）と、TypeScript（config / jwt / outcome / docker / run / cli）に分割。認証情報は `.local/zoom-credentials.env`（`ZOOM_SDK_CLIENT_ID` / `ZOOM_SDK_CLIENT_SECRET`）。JWT は標準入力。終了コード 0 成功 / 1 その他 / 2 設定エラー / 3 認証失敗 / 4 時間切れ。SDK 側 30 秒＋ホスト側 15 秒。確認事項: 終了コードと待ち時間、環境変数名と置き場所、Issue レポートの担当、ダミー認証の可否
- **Codex**: C++ の `init-only` / `auth`。SDK の生出力を出さず固定マーカーだけを解釈、read-only・tmpfs。Git 管理外の JSON から認証情報を読む。認証 30 秒・外側監視 45 秒・猶予 2 秒。成功 / 失敗 / SDK の時間切れ / ローカル期限を区別。C++ の状態処理を SDK の偽物と組み合わせて Vitest からコンパイルしてテスト。確認事項: 待ち時間・終了コード・JSON 方式
- 人間への回答: 両方の提案値で可。Issue レポートは開発チームが書く。Codex には「SDK のない CI と Mac で `npm run test` が通る分け方、コンパイラが無いときに黙って飛ばさない」、Claude Code には「docker の子プロセスに Secret を含む環境変数を渡さない」を追加で指示

### ADR の候補（finish-issue で採否を決める）

- SDK を動かす部分は Docker 上の小さな C++、JWT 生成・判定・プロセス管理は TypeScript 側に置いてテストする（両計画で共通）
- 認証情報はリポジトリ外のローカルファイル（env 形式 / JSON 形式で両計画が異なる）、JWT は標準入力で渡す（共通）

## 9. 学びと次の作業

- **SDK の JWT の有効期間**: 7.1.5.4434 は exp − iat がちょうど 1800 秒の JWT を同期的に `SDKERR_INTERNAL_ERROR` で拒否した（PR #2 実装者の `--network none` での比較）。公式資料の「最小 30 分」と食い違う。後続の SDK 利用で前提になるので、ADR か README に残す候補
- **PR #3 の同期エラーの原因**: JWT の有効期間（上記）が有力。`--read-only`・`--cap-drop ALL`・tmpfs などの強化が影響している可能性も否定できていない（未確認）
- **二重実装で得た改善**: PR #3 の中断処理の作り（`--init`、シグナル処理）を PR #2 の修正に取り入れた。PR #2 の結果の区別（同期エラーと callback）は、PR #3 の必須指摘の判断材料になった
- **品質レビューの独自性（暫定）**: PR #2 では、品質レビューが Docker エラーが見えない問題（推奨3）と、秘密の境界の絞り込みが未テストの問題（推奨4）を独自に見つけ、修正に含めた。中断と後始末の問題は相互レビューと重複した。PR #3 では、品質レビューが設定読込中の中断不能（特殊なファイルの場合）を独自に見つけた

- **SDK の版**: ARM64 版の 7.1.5.4434 は本物の認証情報で結果が返らず、7.2.1.5860 で認証に成功した（→ [ADR 0002](../decisions/0002-zoom-sdkは7.2.1.5860のarm64を使う.md)）
- **時間切れの表示**: 検証プログラム自身の待ち時間切れを「SDK の時間切れ」と表示していた。判定のテストが結果行のコードの有無を区別していなかったのが原因で、修正済み
- **修正で入った不具合**: 2回とも、展開・後始末のシェル処理で起きた（R1、R4）。相互レビュー担当が修正前後を比べて再現し、見つけた
